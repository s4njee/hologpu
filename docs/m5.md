## Standalone measurements

[Chrome defaults](benchmarks/m5-chrome.json) and [WebKit defaults](benchmarks/m5-webkit.json) contain 42 rows: three runs of each of seven effects per engine. All current typed defaults, seed 7, physical 512² display, DPR 1, resolution scale 1 and fixed work quality are checked against the actual runtime. Each run completes 150 fixed updates, discards 30 warm-up frames and measures 120 workloads. Actual pass labels, input fixtures, texture taps, dimensions and stable logical allocations are validated outside the timed interval.

These standalone runs use owned deterministic fixtures: two linear HDR cards, a text coverage mask, and a signed two-sine waveform with its actual DFT. Fluid obstacles uses two packed rectangles and its default 256² grid and 32 pressure iterations. Individual research notes contain generated parameter tables and measured rows. Standalone timing excludes DOM geometry, CSS polling and live media; it cannot establish the attached-page exit criterion.

CPU encoding, encoding-through-queue-completion wall latency, summed actual pass timestamps and observed rAF cadence measure different boundaries. Timestamp precision and overlapping pass intervals can make summed GPU intervals exceed wall completion; the sum is not whole-frame elapsed time. Serialized timestamp readback contributes to observed cadence. Compilation/initialization are excluded, machine load is uncontrolled, and logical allocation bytes are not VRAM.

## Attached-page measurements

The final [Chrome page record](benchmarks/m5-page-chrome.json) and [WebKit page record](benchmarks/m5-page-webkit.json) pass all six fixed-quality refresh runs. Each measured run includes all six actual Family H attachments at 264 × 220 pixels, 120 shared submissions and 120 actual renders/updates per field, with real scroll-driven uniforms. Completed-work p95 is 6.3 / 6.2 / 6.8 ms in Chrome and 7 / 7 / 6 ms in WebKit. The declared gate compares completed work and median rAF cadence to 110% of each run's idle refresh interval.

The CPU boundary begins at the first field's custom before-frame hook, after that field's automatic radius lookup, and ends at asynchronous shared queue completion. Cadence includes the ordinary scheduler; GPU completion is observed without awaiting it inside the measurement wrapper. The runtime itself admits one scheduled batch until its queue completes. All six fields remain in each batch.

CSS polling measures zero, one and eight bindings separately from GPU rendering; zero bindings perform zero style reads, and active bindings share one computed-style object per visible hook. The [overlay decision](adr/017-overlay-canvas-measurements.md) records both corrected geometry and retained pre-fix captures. Context count falls from six to one, while owned source textures remain 3,967,248 bytes and the overlay adds 384 bytes of rectangle uniforms. Its larger viewport presentation estimate and immediate 60-pixel stale coordinates favor in-flow presentation for this page. These box observations do not measure compositor input-to-photon latency.

## Adaptive response

The [matched six-Family-H failure before the adaptive fix](benchmarks/m5-page-software-before-adaptive-fix.json) used the same six effects and requested layout as the native page, with real SwiftShader queue completion. In its 30-second capture it submitted 13 batches, completed nine, and retained four pending batches. No quality event occurred; maximum completed-work latency was 12.83 seconds and maximum cadence gap was 3.79 seconds. Competing external GPU jobs affected load, but the absence of any response exposed the controller's long observation warmup and unbounded scheduler submission rate. This gate has not passed. The runtime now bounds scheduled work to one unfinished batch and responds immediately to severe real completion delays within declared quality bounds. The [corrected cold-adaptive record](benchmarks/m5-page-software.json) passes with actual quality events and GPU completion. Adaptation starts at attachment creation and is never reset before the timed capture. All six fields reduce their requested 264 × 220 backing to 66 × 55, with resolution and work scales of 0.25. In 30 seconds, 177 shared batches are submitted, 176 complete after the real downshift, and all six fields render 177 times. Maximum completion is 459.7 ms and maximum cadence gap is 459.9 ms, below the declared one-second stall threshold; the timed queue depth is bounded at one.

Cold startup is retained rather than silently discarded: status readiness takes 6.75 seconds, input/layout settling 6.82 seconds, and the initial queue drain 43.7 ms. The early recorder observes 29 startup GPU completions with maximum 403.8 ms, maximum pending depth two and no pending work when capture begins. Startup includes shader/input initialization; its pending depth also includes explicit input work outside scheduled frame admission. These are measured software-adapter results under disclosed uncontrolled external load. They prove a weaker execution-path response on this host, not performance on an unmeasured physical laptop.

## Reproduce

Build the production preview before measurements, and run GPU jobs sequentially so they do not contend:

```sh
pnpm test
pnpm typecheck
pnpm build
pnpm --filter @mk7s/hologpu-playground exec vite preview --host 127.0.0.1 --port 5176 --strictPort
# In a second terminal, with the preview running:
pnpm benchmark:m5-page software adaptive
pnpm benchmark:m5-page chrome
pnpm benchmark:m5-page webkit
pnpm benchmark:m5 chrome
pnpm benchmark:m5 webkit
pnpm test:browser
pnpm exec playwright test --config=playwright.hardware.config.ts --project=chrome-hardware --project=webkit-hardware
```

## Scope of the evidence

Device-loss tests call the actual shared device's `destroy()` and observe rebuilt generations; they do not model operating-system GPU resets. `DomStage.memory` sums field-owned logical allocations and overlay uniform buffers, excluding borrowed `DomRectsInput` buffers; those descriptors expose `bufferBytes` separately. Browser swap-chain image counts, physical VRAM and driver overhead are unknown. Software pressure measures SwiftShader as a weaker execution path on the development machine; physical weaker laptops remain a separate device-class validation task. The retained six-fluid software stress failure must remain visible alongside the matched six-Family-H result.
