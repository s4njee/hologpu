## Automated and native validation

- `pnpm check`: formatting, all workspace/test TypeScript, 3 unit tests, package/app production builds, and 14 Chromium/SwiftShader browser cases.
- `pnpm test:hardware`: 18 browser cases across installed Chrome 154, Playwright Firefox 155 (headed), and Playwright WebKit 26.6.
- Native Safari 27: six canvases visibly render; compute/pixel verifier passes with max byte error 0 and repeatable output at DPR 2 (988×480) and zoom DPR 1.7 (840×408). This checks the actual Safari app separately from Playwright WebKit.
- Native Firefox 157: six canvases visibly render with the correct transparent/opaque halves. Resize, scroll, buffer correctness and teardown are covered separately by the headed Firefox automation.
- Built production preview: compute/pixel verifier passes with repeatable readback; the compiled `@mk7s/hologpu/spikes` package export also imports successfully.
- No remote CI job, public deployment or package publication was performed.

## Recorded benchmark runs

Each range below covers three run means. Every run uses seed 7, 30 warm-up frames, 180 measured frames, a 1200×900 viewport and DPR 2. The page scrolls while every canvas renders. All six surfaces are 988×480 backing pixels. Chrome/WebKit were headless; Firefox was headed because its headless adapter request failed on this host.

Raw records: [Chrome](benchmarks/m0-chrome.json), [Firefox](benchmarks/m0-firefox.json), [WebKit](benchmarks/m0-webkit.json). The records include p50, p95, max, adapter information, sizes, maximum scroll position and validation errors. All recorded render/compute errors and shader diagnostics are empty.

These intervals measure browser scheduling cadence, not GPU pass duration or a guaranteed presentation rate. In particular, headed Firefox and headless Chromium do not have the same frame clock. Do not use this table to rank browser performance. Background applications and thermal state were not controlled; the runs establish feasibility, not a hardware performance budget for later effects.

Six float targets have 22,763,520 bytes (21.71 MiB) of logical payload, versus zero owned intermediate texture bytes in direct mode. Both use 208 bytes of owned buffers. One canvas image per surface would add 11,381,760 bytes (10.85 MiB), but the browser's image count and driver/compositor costs are not exposed. Actual resident GPU memory was not measured.

## Foundations kept deliberately experimental

The spike implementation is exposed through `@mk7s/hologpu/spikes`; the core public entry and effects/DOM packages are reserved scaffolds. There is no premature effect definition, production scheduler, custom element, or library device-recovery contract. Read the Holochart v2 device, resource, loop and shader patterns again when implementing those equivalents in M1. Q1–Q6 in the plan remain open and did not block M0; minimal local styles keep this milestone self-contained.
