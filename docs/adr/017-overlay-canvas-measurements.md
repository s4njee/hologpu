# ADR 017: retain in-flow presentation; keep the overlay as a research mode

Status: accepted research decision, based on the final production measurements and retained failed baseline captures.

One shared device and one presentation canvas per attachment remain the default. The overlay reduces presentation context count, but retains all six source targets, adds a full-viewport presentation image and requires JavaScript to repaint layout coordinates. That tradeoff does not improve this page's estimated presentation memory or its immediate response to scrolling.

## Measurement protocol

`node scripts/benchmark-m5-page.mjs chrome` and `webkit` use the built production playground at `http://127.0.0.1:5176`. The page uses six actual Family H attachments on Apple/Metal, with independent instances and a shared device. The declared layout is a 1440 × 1000 viewport at DPR 1, three columns of 220 CSS-pixel-high cards, and a 760 CSS-pixel-high stage. Each full-quality source backing is 264 × 220 pixels, for 348,480 source pixels total. The six IDs are `border-energy`, `spotlight`, `image-hover`, `text-dissolve`, `audio-spectrum` and `scroll-scene`.

The native refresh test runs the ordinary shared scheduler. It drives real scrolling for CSS/scroll uniforms, captures every field's actual update and render counts, and observes shared queue completion asynchronously. The measurement wrapper observes completion without awaiting it inside rAF. The actual runtime admits one scheduled batch until its queue completes; other page rAF callbacks remain available while it waits. The CPU/queue interval starts in the first field's custom before-frame hook; automatic hooks registered earlier on that first field are outside this boundary. Each of three runs has 30 warmup submissions and 120 measured submissions. The gate requires at least 95% of completed intervals below 110% of that run's idle median rAF interval and workload median cadence below the same deadline. Fixed quality, seed 7, scale 1 and time scale 1 keep the workload reproducible.

CSS cost is isolated using the public production `bindCSSParameters` API, selecting 0, 1 or 8 scalar bindings. Each of three runs samples 30 warmup and 120 measured visible frame hooks. No GPU rendering is included in that cost region. Zero bindings register no polling hook and perform zero computed-style reads; one and eight bindings each use one computed-style object per hook. The eight-binding cap bounds work; these measurements do not establish that eight is an optimal universal limit.

Scroll drift is sampled over 120 alternating programmatic 60-pixel scroll changes. For in-flow presentation, the presented box is the canvas's current DOM box. For the overlay, it is the box last encoded into the GPU composite. The actual source-canvas content box is used on both sides; author borders are recorded separately. The post-update sample follows two rAF callbacks and shared queue completion. These CPU observations cannot see compositor-only wheel scrolling, establish input-to-photon latency, or prove zero shader-content latency. Settled screenshots provide an additional visual check.

## Final native findings

The [final Chrome record](../benchmarks/m5-page-chrome.json) and [final WebKit record](../benchmarks/m5-page-webkit.json) passed all six native refresh runs. Chrome completed-work p95 was 6.3 / 6.2 / 6.8 ms, with median cadence 16.6 / 16.6 / 16.7 ms. WebKit p95 was 7 / 7 / 6 ms, with median cadence 17 / 17 / 17 ms. Every measured completion was inside its deadline, approximately 18.37 ms in Chrome and 18.7 ms in WebKit. Every field rendered and updated exactly 120 times in each measured run, at full resolution and fixed quality, without validation errors.

These are headless browser refresh measurements on an Apple-silicon host, rather than a claim about every physical display mode. Chrome was 154.0.8037.98 and WebKit 26.6. No independent LCD benchmark job was observed before the final native sequence; machine-wide background load remains uncontrolled.

| Actual presentation contexts         |                6 |                  1 |
| Owned source texture bytes           |        3,967,248 |          3,967,248 |
| Additional overlay rectangle buffers |                0 |                384 |

| One RGBA8 presentation image         |  1,393,920 bytes |    5,760,000 bytes |
| Three RGBA8 presentation images      |  4,181,760 bytes |   17,280,000 bytes |

Both modes also own 752 source buffer bytes. The full-viewport overlay's estimated presentation image is 4.13 times the aggregate in-flow images for this sparse page. These are logical RGBA8 one-image and three-image estimates. Browser swap-chain image count, physical VRAM allocation, alignment and driver overhead are not observable through WebGPU; context count alone does not prove a memory saving.

Both engines showed zero immediate box drift for in-flow canvases and up to 60 pixels of stale overlay coordinates immediately after a 60-pixel scroll. Both reached zero measured box drift after the bounded settling sample. The settling procedure took a median 33.6 ms in Chrome and 34 ms in WebKit, roughly two refresh intervals; that duration is not an estimate of the overlay's actual visual lag.

The final [Chrome in-flow](../benchmarks/m5-in-flow-chrome-scroll.png), [Chrome overlay](../benchmarks/m5-overlay-chrome-scroll.png), [WebKit in-flow](../benchmarks/m5-in-flow-webkit-scroll.png) and [WebKit overlay](../benchmarks/m5-overlay-webkit-scroll.png) screenshots were inspected. Surface tops align with the cards, and effects stay within the rounded, hidden-overflow edges. The overlay demonstration deliberately clears host backgrounds to transparent so the fixed canvas is visible underneath accessible content; transparent border/text regions therefore have different background colors. This verifies settled alignment and clipping, not whole-image color equivalence or transparent behavior for arbitrary opaque author backgrounds.

For isolated CSS reads/parsing, Chrome p95 was 0.2 ms with one property and 0.2–0.3 ms with eight; run means were approximately 0.10–0.12 ms and 0.13–0.14 ms respectively. WebKit p95 was 1 ms with either binding count, with means approximately 0.26–0.32 ms. The timers are visibly quantized, particularly WebKit's integer-millisecond samples. These results cannot justify a precise cross-engine speed ratio or a claim that eight properties cost exactly the same as one. All selected properties actually changed; each run recorded 120 style reads, with 120 parameter applications for one property and 960 for eight.

## Research corrections and software pressure

The [initial Chrome](../benchmarks/m5-page-chrome-before-clip-fix.json) and [initial WebKit](../benchmarks/m5-page-webkit-before-clip-fix.json) records are retained. Their [in-flow](../benchmarks/m5-in-flow-chrome-scroll-before-clip-fix.png) and [overlay](../benchmarks/m5-overlay-chrome-scroll-before-clip-fix.png) screenshots exposed a limitation that CPU boxes missed: collapsed slotted-heading margins displaced the canvas about 23 pixels below its host, and the overlay did not reproduce hidden overflow and rounded clipping. The encoded canvas boxes aligned while pixels spilled beyond cards. The wrapper now establishes an independent formatting context, and the overlay reproduces authored clipping while permitting overflow where the author allows it. Final evidence above was regenerated after that correction.

The [initial matched six-Family-H software capture](../benchmarks/m5-page-software-before-adaptive-fix.json) failed. It submitted 13 frames and completed nine workloads in 30 seconds, with four pending workloads, no quality events and every backing still at 264 × 220 pixels. Maximum completed-work latency was 12.83 seconds and maximum cadence gap was 3.79 seconds. Independent user LCD browser/GPU tasks were active; the raw record identifies that competing load, so these timings are not uncontended capacity measurements. The old controller's 30-observation warmup exceeded the available completed observations. This capture enabled adaptation after fixed-quality startup; that protocol and the runtime were corrected rather than discarding the failed outcome.

The [final matched software capture](../benchmarks/m5-page-software.json) starts adaptation from first attachment creation and retains cold quality events, actual startup GPU completions and readiness/drain durations. The declared measurement CSS is inserted into the production HTML head before creation; the same six IDs and 264 × 220 CSS-pixel sources request scale 1 and DPR 1. Parameters begin with the schema defaults and receive the production attachment's geometry and scroll uniforms. The capture preserves adaptations and simulation state rather than resetting quality after startup.

Cold status readiness took 6.75 seconds and visible/input readiness 6.82 seconds, including compilation and browser protocol checks. The initial queue drain took 43.7 ms. All 29 observed startup GPU workloads completed, with p95 363.7 ms and maximum 403.8 ms; maximum observed startup submission gap was 412.5 ms, with at most two pending workloads and none pending at capture. These observations do not claim instant initialization or complete timing coverage before the first attachment became ready.

All six fields actually reduced their backings to 66 × 55 pixels, resolution scale 0.25 and work scale 0.25. During the bounded 30-second timed capture, all six rendered 177 times; 176 shared GPU workloads completed after a real quality downshift, with one pending workload at capture end. Completed-work p95 was 249.1 ms and maximum 459.7 ms; cadence p95 was 249.2 ms and maximum 459.9 ms. No validation errors or one-second cadence/completion stalls were observed. The adaptive gate passed: real reduction, at least five completed GPU workloads after reduction, and continuing rendering. It demonstrates slower ongoing progress at reduced quality, rather than native refresh rate on the software adapter.

SwiftShader is a real software adapter and a reproducible weaker-capacity proxy; it does not validate a physical weaker laptop. Independent user jobs may have remained active during this capture, so the record discloses competing load. Native and software timings are separate scenarios rather than controlled hardware speed comparisons.

The retained [six-fluid software stress record](../benchmarks/m5-stress-six-fluids-software.json) is a different, extreme workload: six default 256² `fluid-obstacles` solvers with 32 pressure iterations each, captured before the overload correction. In 30 seconds it submitted seven frames, completed four GPU workloads and retained three pending workloads. No downshift occurred. Maximum completed-work latency reached 13.06 seconds and maximum cadence gap reached 11.79 seconds, without validation errors. Its gate failed. This failure remains visible; the final matched Family H pass does not establish that six expensive fluid solvers now run without stalls, and that extreme workload was not recaptured.

## Decision and remaining limits

Keep in-flow attachment presentation as the default. It follows layout without rewriting viewport coordinates, naturally participates in author clipping and uses smaller presentation images for this page. Keep the overlay opt-in for investigating high context counts, densely overlapping surfaces or intentional effects beyond element boundaries. Any claim of improved memory needs the actual page's coverage ratio and clearly labeled allocation estimates. Any claim about scroll latency needs a compositor-aware capture in addition to these CPU observations. A physical weaker-device run remains untested.
